# Решения

## 2026-10-25 — Тестовый проект

Выбран локальный консольный TaskManager на C#.

Причина: проект достаточно мал для быстрого прогона, но содержит доменные правила, состояние, файловое хранение, ошибки, тесты и возможность поэтапного расширения.

## 2026-10-25 — Граница MVP

В MVP не входят GUI, БД, сеть, синхронизация, авторизация и внешние интеграции.

Причина: сначала проверяем процесс Pi, а не инфраструктурную сложность тестового приложения.

## 2026-10-25 — Ручной прогон Pi

Тестовый проект доведён до состояния для ручной проверки Pi: рабочие файлы `.pi/work`, доменная модель, JSON-хранилище, поиск/фильтрация, CLI и зелёные проверки.

Прогон выполнен в отдельных свежих CLI-сессиях Pi:

```text
Luna → изменение теста → dotnet test 10/10
Opus → проверка diff/spec → APPROVE
Jev → classifier через codemode → typed VERDICT.json
```

Opus не изменял файлы. Jev не выдаёт свободный текст: результат хранится как typed JSON с `stopReason` и вероятностью.

## 2026-10-25 — Интеграция Jev

Для вызова classifier из Pi зарегистрирован provider extension `.pi/extensions/anymodel-classifier.ts`.

Причина: одного описания classifier в `models.json` недостаточно — Pi должен иметь реализацию `classifiers["typesafe-system-one"]`. Extension регистрирует AnyModel endpoint, модель `jev/jev-latest` и transport `typesafe-system-one`.

Проверенный вызов:

```text
provider: anymodel
model: jev/jev-latest
api: typesafe-system-one
stopReason: stop
answers.approved.type: bool
answers.approved.probability: 0.74
```

## 2026-10-25 — Результат ревью

Opus одобрил изменение `Query_CombinesTitleSearchWithPriorityFilter`. Замечание о неотслеживаемом extension-файле относится к гигиене коммита, а не к тесту. Файл нельзя добавлять в коммит случайным `git add .` без отдельного решения.

## 2026-10-25 — Правила статусов

Задача создаётся в статусе `New`, переходит через `InProgress` в `Done`; возврат из `Done` запрещён.

Причина: это минимальное конечное состояние, на котором удобно проверять доменные правила и тестовый цикл Pi.

## 2026-10-25 — Правило фиксации

Pi выполняет локальные изменения и проверки, но не делает push, PR или merge. Коммит выполняется отдельно после проверки пользователем.

Причина: граница ответственности явно исключает удалённые Git-операции.

## 2026-10-25 — Локальный путь extension

`.pi/extensions/anymodel-classifier.ts` сейчас содержит абсолютный путь к установленному локально пакету Pi AI. Это рабочий диагностический артефакт текущей машины, но не переносимая часть проекта. Перед коммитом нужно либо заменить импорт на переносимый вариант, либо оставить файл неотслеживаемым/удалить.

Причина: не закреплять machine-specific путь как проектный контракт без отдельной проверки способа загрузки Pi extensions.

## 2026-10-25 — Jev: Router и Verifier разделены

Jev не является единственным владельцем памяти и не должен одновременно искать весь контекст, маршрутизировать его и принимать финальное решение. Pi хранит контекст, детерминированно собирает кандидатов, применяет policy и записывает файлы.

Перед работой модели используется `Jev Router`: он выбирает из кандидатов релевантные фрагменты, обнаруживает конфликты и сообщает о недостающем обязательном контексте. После работы используется отдельный `Jev Verifier`: он принимает typed-решение по evidence.

Причина: отделить полноту retrieval от модельного отбора и не скрывать ошибки сборщика за уверенным verdict Jev.

## 2026-10-25 — Jev управляет логическим контекстом

Jev расширяется до typed Context Manager. Он может предложить операции `ADD`, `UPDATE`,
`REMOVE`, `RETAIN`, `ROUTE` и `CONFLICT` над логическими фрагментами контекста.
Pi проверяет эти операции по policy, применяет их к физическому хранилищу и формирует
новый manifest. Уже отправленный модели prompt не редактируется.

`TRANSIENT` можно удалить, а `CANONICAL` и `DECISIONS` нельзя менять или удалять молча;
устаревшие фрагменты получают статус `obsolete`, а операция сохраняется в routing log.

Причина: Jev должен управлять жизненным циклом контекста, но не получать неконтролируемое
право менять файлы и канонические решения.

## 2026-10-25 — Слои контекста и provenance

Контекст разделяется на `CANONICAL`, `DECISIONS`, `TASK_STATE`, `OBSERVATIONS`, `HYPOTHESES` и `TRANSIENT`. Каждый фрагмент должен иметь источник, версию/свежесть, authority, status, sensitivity и targetModels.

Причина: свободное резюме модели не должно становиться канонической памятью; нужно различать факт пользователя, решение, наблюдение инструмента, гипотезу и временное состояние.

## 2026-10-25 — Evidence-first verdict

`APPROVE` допустим только при наличии ссылок на фактические evidence: build, test, diff, review и smoke при необходимости. Дополнительные состояния: `REQUEST_CHANGES`, `BLOCKED`, `INSUFFICIENT_EVIDENCE`.

Причина: probability Jev — это сигнал classifier, а не доказательство работы кода; отсутствие доказательств должно быть отдельным состоянием, а не скрытым reject.

## 2026-10-25 — Проверка результатов

Текущий проверенный результат:

- `dotnet build TaskManager.sln` — 0 ошибок, 0 предупреждений;
- `dotnet test TaskManager.sln` — 10/10;
- Jev typed classifier — `stop`;
- workflow Luna → Opus → Jev выполнен.

Следующий шаг — этап 6 плана: контракт контекста и evidence. После него отдельно проверяются Router и Verifier. Судьба диагностического extension-файла решается отдельно и не является частью доказательства качества маршрутизации.
